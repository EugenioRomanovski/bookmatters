# Мобильное обновление, закрытые клубы, друзья и главы

Статус: код готов; миграция production не применена, публикация в production ожидает одобрения изменений правил доступа. Автоматическая проверка отклонила миграцию из-за изменения границ доступа существующих таблиц, потребовав явного одобрения этих изменений. Данные production не менялись.

## Поведение

- На телефоне: системная типографика iOS, полупрозрачные поверхности, плавающая нижняя навигация, карточки с крупными зонами нажатия, формы в нижней панели. Сохранены поля минимум 16px и безопасные отступы PWA.
- Новый клуб: выбор открытый/закрытый и главы/страницы. Главы выбраны по умолчанию; организатор задаёт их число и число недель. Диапазоны создаются автоматически; недель не может быть больше, чем глав/страниц.
- Старые клубы остаются открытыми и сохраняют страницы и планы. Их данные не переименовываются и не преобразуются в главы.
- Закрытый клуб скрыт из общего каталога. Посторонний не может читать его метаданные, участников, план и сообщения даже прямым запросом API. Адресат приглашения видит книгу и описание, но план, состав и обсуждения получает после вступления.
- Друзья общие с Encore/Winenote: поиск по @username, заявки, принятие/отклонение, отмена и удаление. Можно заполнить общий профиль в Bookmatters.
- Организатор закрытого клуба приглашает подтверждённых друзей внутри приложения. У открытого клуба это может сделать любой участник. Получатель видит приглашение во вкладке «Друзья» и может принять или отклонить. Отправитель может отозвать приглашение.
- Приглашения и заявки обновляются при возвращении в приложение, каждые 30 секунд на активном экране и кнопкой обновления.
- Организатор может переключить видимость существующего клуба; текущие участники сохраняют доступ.

## Что меняется в базе

Точная миграция: `database/changes/private-clubs-friends-chapters.sql`.

Только пространство Bookmatters:

1. Новые поля в `bm_clubs`, `bm_stages`, `bm_progress`; nullable поля страниц для клубов по главам, дополнительные проверки согласованности.
2. Новая таблица `bm_invitations` с RLS. Чтение/удаление только отправителем или адресатом; вставка проверяет дружбу, членство и роль организатора закрытого клуба.
3. Меняются шесть RLS-политик: чтение клубов, участников и этапов; вступление в клуб; создание и обновление личного прогресса. Они ограничивают доступ для закрытых клубов и проверяют пределы прогресса.
4. Четыре маленькие SECURITY DEFINER функции в **неэкспонируемой схеме `bm_private`** нужны только для чтения членства без рекурсии RLS. Они всегда используют текущий `auth.uid()`, не принимают чужую идентичность и не изменяют данные. Выполнение PUBLIC отозвано. Это исключение осознанно ограничено внутренними проверками доступа.
5. Два RPC в `public` используют SECURITY INVOKER: создание клуба и ответ на своё приглашение. Анонимное выполнение запрещено.

Таблицы и функции Encore/Winenote, `auth.users`, `profiles` и `friendships` миграция **не изменяет**. Приложение использует существующие права и RPC общих друзей; текущая дружба сохраняется. Данные клубов не удаляются. Новые ограничения могут запретить ранее разрешённые API-запросы, поэтому перед публикацией требуется применение этой миграции и проверка RLS.

## Проверки

`npm run test:db` поднимает отдельный PostgreSQL в WASM (PGlite) и применяет базовую схему с миграцией. Соединения с production в тесте нет. Проверены:

- сохранность старого клуба и плана;
- главы по умолчанию, полное разбиение глав и страниц;
- свободное вступление в открытый клуб;
- изоляция закрытого клуба, его состава, плана, обсуждений и личных заметок;
- запрет приглашений без подтверждённой дружбы и приглашений от обычного участника закрытого клуба;
- принятие/отклонение своего приглашения, запрет обработки чужого;
- отзыв доступа после выхода, переключение видимости организатором;
- запрет спойлеров, недопустимого прогресса и анонимного выполнения RPC.

Production-сборка проходит. Проверка в настоящем мобильном браузере не выполнена: инструмент браузера отсутствует в рабочем окружении.

## Выпуск после одобрения

1. Применить точную миграцию в существующем Supabase Encore (`uvuifuyozscfcowuxdtr`).
2. Проверить таблицы, политики и Supabase advisors; выполнить регрессионный тест с откатом, не сохраняя тестовых пользователей.
3. Слить проверенную ветку в `main`; Vercel соберёт production.
4. Проверить статус GitHub/Vercel и новые файлы на `bookmatters.brainsome.app`.

До миграции preview показывает дизайн, но операции новых функций требуют новой схемы базы. Ветка не заменяет production-версию.
